## C1. F-19 — forwarding-мост: один процесс на проект

**Задача.** В preset-композиции (весь Web GUI) каждая сессия монтирует свой инстанс серверов,
потому что ключ агента уже связан пресетом. Мост: держать **один проектный**
`mcp-client` и на каждую сессию регистрировать в её слое тонкие forwarding-определения,
чтобы вернуть «один процесс на проект».

**Точки опоры в харнессе** (проверены координатором на `ddefc45fbc`):

- `packages/core/tools/src/index.ts:1210` — `get(name: string, scope?: ScopeKey): ToolDefinition | undefined`
- `:1043` — `register(definition: ToolDefinition): () => void`
- `:1240` — `schemas(scope?: ScopeKey): ToolSchema[]`
- `:954` — `presentAs(mode: ToolPresentationMode): () => void`
- `ScopeKey` — тип ключа слоя; найти его определение и семантику видимости до правок.

**Порядок обязателен — сначала доказательство, потом интеграция.**

1. **Спайк.** Новый `tests/bridge.spec.ts`: тест, который доказывает на реальном харнессе, что
   forwarding работает: один инстанс сервера держится на проектном слое; в слое сессии
   регистрируется тонкое определение, исполняющее `execute` проектного; имя видно в
   `schemas(scope)` **именно этой** сессии; второй сессии — свой тонкий слой поверх того же
   инстанса; вызов из двух сессий не поднимает второй процесс/инстанс.
2. **Интеграция** — только если спайк зелёный. Мост живёт в новом `src/bridge.ts`, рантайм его
   вызывает в месте маунта; существующий per-session путь сохраняется как поведение по умолчанию
   ровно до тех пор, пока тесты не переписаны осознанно под общий инстанс.
3. **Если спайк не проходит** — стоп, отчёт-блокер: что именно не даёт харнесс (с `file:line` в
   его чекауте), какие варианты остались. Полуреализацию не оставлять: дерево должно быть
   зелёным и без мёртвого кода.

**Зона записи:** `src/bridge.ts` (новый), `src/runtime.ts`, `src/types.ts`,
`tests/bridge.spec.ts` (новый), `tests/runtime.spec.ts`, `tests/lazy.spec.ts`,

**Не трогать:** `src/notifications.ts`, `src/logs.ts`, `src/ui.ts`, `src/client/**`,

## C2. F-20 — per-file 80% для двух клиентских файлов

**Задача.** Поднять покрытие **на файл** до 80% по четырём метрикам для
`src/client/settings.ts` (~63/59) и `src/client/view.ts` (~64/66) — там хуки (`useSnapshot`,
`useNarrowSettings`, `browserMatchMedia`) и обработчики кнопок, которые сейчас покрыты
частично. Общий порог 80 в `vitest.config.ts` остаётся глобальным.

**Правила.**

- Новые тесты обязаны **утверждать поведение** (значение, текст, вызов, порядок), а не
  «прогнать строки ради покрытия». Тест, который ничего не проверяет, — не выполнение F-20.
- DOM/хуки: использовать `react-dom/server` там, где хватает серверного рендера, и
  **праговый** `// @vitest-environment jsdom` в шапке нового spec-файла там, где нужен
  настоящий DOM (без правок `vitest.config.ts` и без установки новых зависимостей — сначала
  проверить, что `jsdom`/`happy-dom` уже есть в дереве; если нет — обосновать и обойтись).
- **Принуждение к порогу — в `scripts/audit.mjs`:** новая проверка читает
  `coverage/coverage-summary.json` и требует ≥80 по четырём метрикам для этих двух файлов;

## C3. F-21 — уведомления как сервис

**Задача.** Сегодня рантайм пишет событие в три места по отдельности: строку в лог DSH,
`notify()`/анонс снапшота и кольцо `src/logs.ts`. Вынести это в **один** модуль
«событие плагина → потребители», чтобы кольцо, лог и анонс были подписчиками, а не тремя
независимыми записями.

**Контракт сервиса (замораживается):**

```ts
// src/notifications.ts (новый, хост)
export interface PluginEvent {
  readonly at: number
  readonly level: LogLevel            // из src/types.ts
  readonly projectRoot: string
  readonly sessionId?: string
  readonly server?: string
  readonly message: string
  readonly detail?: string
}
/** Одна точка публикации события плагина. */
export function emitEvent(event: PluginEvent): void
/** Подписка потребителя (кольцо, лог, анонс); возвращает отписку. */
export function subscribeEvent(listener: (event: PluginEvent) => void): () => void
```

- `emitEvent` — единственная точка, из которой пишутся **все** пять событий жизненного цикла;
  кольцо и DSH-лог становятся потребителями (или остаются внутри сервиса, но вызываются из
  одного места, а не из пяти).
- Поведение не меняется: те же пять событий, те же уровни (`info`/`up`/`warn`/`error`),
  те же тексты, тот же анонс снапшота после события, тот же `record()` в кольцо.
  Существующие `tests/logs.spec.ts`, `tests/ui.spec.ts`, `tests/runtime.spec.ts` должны
  остаться зелёными **без правки ожиданий**; если ожидание пришлось править — это сигнал, что
  поведение изменилось, и об этом надо писать в отчёте, а не «поправить тест».
- Новый `tests/notifications.spec.ts`: порядок публикации, попадание в кольцо и в лог,
  отписка потребителя, `emitEvent` не бросает в вызывающий код.

**C3.1 Поправка после интеграции (координатор, 2026-09-18).** Требование «поведение не
меняется» оказалось сильнее буквального интерфейса C3: у хостового лога своя типографика, и
через одно поле `level` она поехала. Поэтому в `PluginEvent` добавлены два поля, а интерфейс
считается замороженным в этом виде:

```ts
  /** Точный текст строки DSH-лога; отсутствует — строка берётся из `message`. */
  readonly line?: string
  /** Severity хостового лога, когда она отличается от `level` вкладки. */
  readonly logLevel?: LogLevel
```

Правило: **`level` — это строка вкладки «Логи»** (`info`/`up`/`warn`/`error`), **`logLevel` и
`line` — хостовый лог**, и он обязан остаться таким, каким был до F-21:
`mounting <сервер> for session <id> in <root> (trigger: …; <sharing>)` — `info`,
`<сервер> is up in <root> — its tools are visible to session <id> after <d>` — `info`,
`unmounting <сервер> in <root> — <reason> (it ran for <d>)` — `info`, `<detail>` ошибки
маунта — `warn`, `<detail>` стойла — `warn`. `src/runtime.ts` заполняет `line`/`logLevel` во
всех пяти точках, `logConsumer` предпочитает их.

Одна оговорка: **хвост `sharing` в строке `mounting` — не байт-в-байт**, и это следствие C1, а
не регрессия. Мост (F-19) добавил третий способ держать инстанс, поэтому у строки появилось
новое окончание (`… forwarded into this session's own layer`) там, где раньше было только «one
shared instance…». Форма строки, порядок полей и уровень — прежние; меняется ровно то слово,
которое описывает изменившуюся архитектуру.
- Зона записи: `src/notifications.ts` (новый), `src/runtime.ts`, `src/logs.ts` (только если
  кольцо становится подписчиком), `tests/notifications.spec.ts` (новый),
  `docs/history/logs-parity.md` §«Диагностика»/README там, где описан путь логирования.
- Не трогать: `src/bridge.ts`, `src/client/**`, `scripts/audit.mjs`, `tests/runtime.spec.ts`,
  `tests/lazy.spec.ts`, `tests/bridge.spec.ts`.
